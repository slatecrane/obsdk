# OP Financial Group integration notes

OP Financial Group (OP Pohjola) is Finland's largest bank group. Its PSD2 APIs cover every OP
cooperative bank through one API. The integration registers personal and business customers in FI
for account information (accounts, cards, balances, transactions) and payments (SEPA, scheduled
SEPA, foreign payments).

| | Sandbox | Production |
|---|---|---|
| API and token endpoint | `https://psd2.mtls.sandbox.apis.op.fi` | `https://psd2.mtls.apis.op.fi` |
| Authorisation page | `https://authorize.psd2-sandbox.op.fi/oauth/authorize` | `https://authorize.op.fi/oauth/authorize` |
| Client authentication | mTLS + `client_id`/`client_secret` + `x-api-key` | the same |
| Certificates | generated by OP (`sandbox-tpp` API), no QTSP needed | QWAC + QSealC |
| User login | OP's sandbox login page (test users below) | OP's login page or the OP mobile app |

Built from the OP Developer pages (TPP setup, AIS authorization flow, PIS v2 workflow) and the
OpenAPI documents (AIS v1.1, PIS v2.0).

## What the integration needs

`Info.Requirements` lists these; `banks/op/sandbox.env.example` shows where each comes from.

- `api_key` (`Config.Extra`): the API key of an app on op-developer.fi with the PSD2 AIS and PIS
  products. Sent as `x-api-key` on every call except the token endpoint.
- `client_id`, `client_secret`: from dynamic client registration (`POST /tpp-registration/register`
  with a registration JWT that holds a software statement, both signed with the QSealC key).
- `redirect_url`: one of the `redirect_uris` given at registration.
- The QWAC as mTLS client certificate in `Config.HTTPClient` (`op.HTTPClient`).
- `seal`: the QSealC key, RSA (RS256) or P-256 (ES256). `KeyID` is its `kid` in the JWKS given at
  registration (`software_jwks_endpoint`).

In the sandbox, `go run ./banks/op/sandboxsetup` does all of this with only the API key: it has OP
generate a sandbox TPP with QWAC and QSealC keys (`POST
https://sandbox.apis.op.fi/psd2-sandbox-tpp-generator/sandbox-tpp`), writes them to
`banks/op/cert/`, registers a client using the generated public JWKS URL and prints the env values.
OP deletes generated TPPs now and then: rerun it then.

Sandbox users: `88888881` or `88888882`, password `1122`, key code `1122`.

## Flows

**Connect**:

1. Client credentials token: `POST /oauth/token` with `grant_type=client_credentials&scope=accounts`
   and the client id and secret in the form. OP takes one scope per request.
2. Authorisation: `POST /accounts-psd2/v1/authorizations` with `{"expires": ...}` (at most 180 days,
   the default) → `authorizationId`, status `Unauthorized`. This is a continuous authorisation; it
   reaches 90 days of history.
3. Redirect: `{auth}?request=<JWT>&response_type=code id_token&client_id&scope=openid accounts`. The
   request object is signed with the seal key and carries `aud`, `iss`/`client_id`, `redirect_uri`,
   `state`, `nonce`, `max_age`, `iat`/`exp` and the authorization id under
   `claims.userinfo.authorizationId` and `claims.id_token.authorizationId`, with
   `claims.id_token.acr` = `urn:openbanking:psd2:sca`. `aud` is `https://mtls.apis.op.fi` (the value
   OP's docs show; `Extra["aud"]` overrides it).
4. Callback: `code`, `state` and `id_token` in the **fragment**; errors in the query (`error`,
   sometimes `description`). The id token is not validated: the code exchange over mTLS with the
   client secret authenticates the result.
5. Code exchange: `grant_type=authorization_code&code&redirect_uri` → access token (1 hour), refresh
   token (45 days, renewed on refresh).

**Refresh**: `grant_type=refresh_token`. `invalid_grant` means the user must log in again.

**Disconnect**: `DELETE /accounts-psd2/v1/authorizations/{id}` with a client token. OP asks AISPs to
revoke this way when the user ends the service. The sandbox revokes an unapproved authorization
(`200`, status `Revoked`) but answers `404 "Authorization … not found"` for an approved one, which
`GET` still shows as `Authorized`. So on a 404 the SDK reads the authorization and reports the
consent under `Failed` while it is still live, instead of counting it closed.

## Behaviors worth knowing

- **Accounts carry their balances**: `netBalance` (available, cover reservations deducted) →
  `interim_available`, `grossBalance` → `interim_booked`, `counterBalance` (euro value of a foreign
  currency account) → `other`. `Balances` reads `/accounts/{id}`.
- **Cards** (`/cards`) are listed as accounts with `ID` `card~<cardId>`, `Type: CARD` and a
  `MASKED_PAN`. A card has no currency field (OP cards are in euros, so the SDK sets EUR) and no
  single-card endpoint (`Balances` finds it in the list). Its `statementBalance` and
  `authorizedOutstandingAmount` are used credit, so they are negated.
- **Transactions have no date filter**: the listing takes only a `continuationToken`. The SDK filters
  each page by booking date (payment date when there is none) and puts the window into the cursor; a
  page can come back empty with a `NextCursor`. OP lists newest first (sandbox), so paging stops at
  the first page that reaches before `From`. There are no pending transactions.
- **`archiveId` is not unique** (related transactions with several recipients share one), so it is
  `EntryReference`, not `ID`.
- **Card transaction amounts are what was spent**: positive purchases become debits, negative ones
  (refunds) credits. Assumed from the spec's example.
- **Unattended access**: OP allows 4 requests per 24 hours under one authorisation without the user.
- **Errors** are `{"type": SECURITY|VALIDATION|TECHNICAL|BUSINESS, "message", "violations": [{"type",
  "path", "message"}], "id"}`; the first violation's type becomes `APIError.Code`, `id` the request
  id. Some failures are HTML pages.

## Payments

| Type | Endpoint | Notes |
|---|---|---|
| `sepa` | `/payments-psd2/v2/sepa-payments` | EUR. OP sends SEPA Instant when it can (`Credited`). |
| `sepa` + `execution_date` | `/payments-psd2/v2/scheduled-sepa-payments` (`dueDate`) | OP executes it on the date; cancellable until then. |
| `crossborder` | `/payments-psd2/v2/foreign-payments` | Any currency; payee name (35), account (IBAN or BBAN), BIC or clearing id, 2 address lines + country, message required. |

1. Client token with `scope=payments`.
2. Each transfer: `POST` with the JSON body, `x-jws-signature` (detached JWS of the exact body,
   `header..signature`, signed with the seal key), `x-idempotency-key` (one per transfer, max 40
   characters). The first response opens a bundle (`authorizationId`); further transfers send it in
   their body. Up to 20 transfers per request (OP documents no limit). If a later transfer fails,
   the bundle is revoked.
3. Redirect as for Connect, with `scope=openid payments` and the bundle's authorization id.
4. Code exchange, then `POST .../{paymentId}/submit` for each payment with the user's token. The
   body must be an empty JSON object `{}`: without a body OP answers `400 VALIDATION "Bad request"`.
   OP says to submit right after approval. The response says how OP sends it (`executionType`,
   e.g. `SCT_INST`).
5. Status: `GET .../{paymentId}` with a client token.

A SEPA payment needs a message (140) or a reference: a Finnish reference (scheme `FI`, 4–20 digits
with a check digit) or an RF reference. The SDK checks this before calling OP. A payee with a
non-Finnish IBAN needs an address (up to 4 lines of 35) and a country.

Status mapping: `Unauthorized`, `Authorizing` → `received`; `Authorized` → `accepted`; `Accepted`,
`SubmissionPending`, `AwaitingDueDate`, `AwaitingFunds`, `Processing` → `in_progress`; `Debited`,
`Credited` → `completed` (final); `Rejected` → `rejected`; `Revoked`, `Cancelled` → `cancelled`. A
bundle reports its least advanced status, or `partially_accepted` when some transfers were refused.
Submit errors of type `InsufficientFunds`, `PaymentFail`, `Payee` or `ValidPayerAccount` become
`PaymentRejectedError`.

**Cancel**: a bundle the user has not approved is revoked (`DELETE
/payments-psd2/v2/authorizations/{id}`, client token, no user). An approved payment that is not
executed (in practice a scheduled one) needs the user's approval: a redirect with
`scope=openid payments:delete`, the payment id in the claims and `acr` values
`urn:openbanking:psd2:sca` and `urn:openbanking:psd2:ca`; then `DELETE .../{paymentId}` with that
token. One payment per approval.

Not implemented: recurring SEPA payments, the SCA exemption flow (small payments reusing an earlier
approval), verification of OP's response signatures (`x-jws-signature` on every PIS response).

## Verified against the real sandbox (FI personal, 2026-10-17)

Scenarios `banks/op/testdata/live-fi-*`, user `88888881`:

- `sandboxsetup`: sandbox TPP and certificates generated, client registered (RS256 keys).
- Connect: client token, authorization (`expires` 180 days), redirect with the signed request object
  (`aud` `https://mtls.apis.op.fi` accepted), callback in the fragment, code exchange; 2 accounts.
- Accounts and balances (`netBalance`, `grossBalance`); `/cards` answers `[]` for this user.
- Transactions: 32 on one page, newest first, back about three months, no continuation token.
- Refresh.
- SEPA payment of €1.50: created with the detached JWS, approved, submitted (`Accepted`, sent as
  `SCT_INST`), then `Credited` on a status read with a **client** token.
- Dated SEPA payment (`scheduled-sepa-payments`, `dueDate` 12 days ahead, RF reference): created,
  approved, submitted (`Processing`). The sandbox executed it at once (`Credited`).
- Cancel before approval: the bundle is revoked (`Revoked`) without the user.
- Disconnect of an approved authorization: refused with 404 (see Flows), reported as failed.

Sandbox behaviours, not seen as API rules: client and user access tokens last 5 minutes (`expires_in`
299; the docs say 86399 and 3599); revoking does not stop data access; a dated payment executes immediately.

## Still assumed

- Cancelling an approved, not yet executed payment (the `payments:delete` redirect): the sandbox
  executes dated payments at once, so it ran against a fake server only.
- Bundles of several transfers and foreign payments: fake server only.
- Cards: the sandbox user has none, so card balances and transactions (and the amount sign) are
  untested.
- Business customers: same API; the company representative needs an extra access right from the
  company before approving. Not testable in the sandbox.
- Production: written from the docs; needs a licence and real QWAC/QSealC.
